# Feature 317 deployed benchmark (devnet bench sidecar), 2026-11-04

Session-read capacity of the 317 build on AWS, from 1,000 to 7,500 nonce
polls/s, and what limits it. First deployed run of the `devnet-bench-*`
profiles; the environment was the temporary `guardian-bench` service created
by `scripts/guardian-bench-env.sh` and torn down after the session.

## Summary

- Every run completed with **zero failures** (about 11.8 million session
  reads in total), but zero failures is not "held": past the ceiling the closed-loop
  clients slow down and latency grows to seconds instead of requests failing.
- On one `db.m7g.large` (2 vCPU), session reads are limited by the database,
  and the limit moved as each cause was removed:

  | Build / setting | Ceiling (nonce polls/s) | Limited by |
  |---|---:|---|
  | 317 as committed (`0f0c600b`) | about 4,100 | WAL flush: one durable commit per read |
  | + async commit (experiment only) | about 4,500 | database CPU |
  | + typed admission call (driver fix) | about 4,850 | WAL flush |
  | + driver fix and async commit, 4 server tasks | **about 7,100** | database CPU |

- The cost per read is mostly overhead, not query work. The biggest remaining
  items are a single shared advisory lock taken by every read, partition
  routing, and one transaction (and commit) per read. Removing them is
  expected to reach the 10,000 reads/s target on the same instance class;
  that is an estimate to be measured locally first (see Next steps).
- Found and fixed along the way (uncommitted): every raw `diesel::sql_query`
  is prepared again on each call, doubling round trips and transactions; the
  ECS harness lost worker results larger than one CloudWatch event or page.

## Setup

- Bench environment: ECS service `guardian-bench` in `guardian-cluster`
  (devnet account), built from `0f0c600b` (server 0.19.0-rc.1), Fargate ARM64,
  2 tasks of 2 vCPU / 4 GB (4 tasks in the last run), pool size 32 per task.
  Database: RDS PostgreSQL 17.9, `db.m7g.large`, single-AZ, gp3 100 GB, direct
  route (no RDS Proxy), `sslmode=require`, Performance Insights on.
- Server settings: canonicalization off (bench-only image patch, so pushed
  deltas commit at once), proving, release sweep and rate limiting off,
  `GUARDIAN_ENV=prod`. Bench-only ACK identity from `ack-keygen`, signed in
  memory, so write latency excludes the KMS round trip a KMS-backed
  deployment pays.
- Load: `run-prod-benchmark-ecs.sh` with 4 Fargate workers in the same VPC,
  session credentials (ECDSA), 60 s warmup, 420 s measured. Readers poll the
  canonical nonce; 3 readers per writer are cosigners and fetch state after
  each write; writers push every 10 s (proposal, approval, push).

  | Profile | Users | Readers / writers | Target nonce polls/s | Writes/s |
  |---|---:|---|---:|---:|
  | `devnet-bench-r1-1k` | 2,010 | 2,000 / 10 | 1,000 | 1 |
  | `devnet-bench-r2-2500` | 5,025 | 5,000 / 25 | 2,500 | 2.5 |
  | `devnet-bench-r3-5k` | 10,050 | 10,000 / 50 | 5,000 | 5 |
  | `devnet-bench-r4-7500` | 15,075 | 15,000 / 75 | 7,500 | 7.5 |

r1 and r2 held their targets with low latency. Every r3 and r4 run is
saturated: throughput is close to the ceiling of that configuration and the
latency is queueing. Writes wait in the same queues as the reads, and since
the clients are closed-loop, saturation shows up as missed workload rather
than failures: r3 runs completed 2.9 to 3.5 writes/s of the intended 5, and
r4 4.97 of 7.5. Read overload therefore suppresses writes. Worker CPU stayed
at 15% to 26%, so the load generator was never the limit.

## Bottlenecks, in the order they appeared

### 1. One durable commit per read (WAL flush)

Each session read runs `guardian_admit_session_read`, which inserts a record
of the read (the `unique` replay policy) and commits. In r3 (committed build)
Performance Insights showed 20.4 average active sessions, 17.7 of them waiting
on `LWLock:WALWrite` and 18.6 inside the admission function; disk write IOPS
were only about 370/s, so Postgres was already grouping commits. The
ceiling is how fast the instance can flush WAL for about 4,000 commits/s.

Database CPU grew linearly from r1 to r2 (29% at 1,000/s, 63% at 2,500/s);
extending that line reaches 100% at about 4,100/s, which is where r3 stopped.
CPU and the flush queue ran out at nearly the same point.

Async commit (`synchronous_commit=off` for every server connection, set
through the database URL; experiment only) removed the flush wait (database
load 20.4 to 2.3 sessions) but gained only 9%: database CPU became the limit
at about 0.43 ms per read.

### 2. Every raw SQL query is prepared on every call

The database reported about 9,200 commits/s for 4,500 reads/s. Diesel marks
every `sql_query` (and `dsl::sql` literal) as unsafe to cache, so diesel-async
prepares the statement again on every call: a separate round trip that
Postgres closes as its own transaction, then the execution. Measured locally
with the server's diesel 2.2.12 / diesel-async 0.5.2: 200 calls of
`sql_query` cost 412 commits, 200 calls of a typed query cost 213.

Fix: the admission, session floor and wallet floor CAS calls are now typed
(`define_sql_function!`), so their statements are prepared once per
connection. On RDS this gave 1.03 commits per read, database CPU per read
0.44 to 0.30 ms, and +18% reads/s with normal commits (r3 driver fix). The
limit returned to the WAL flush (`LWLock:WALWrite` 19.9 of 22 sessions,
database CPU 73%).

### 3. Server CPU and uneven replicas

With the driver fix and async commit on 2 server tasks, the database was
nearly idle (0.6 active sessions) yet throughput fell to 4,047/s. Requests
were split evenly between the two tasks (18,694 and 18,760 reads in the same
10 s), but one task spent 817 us of CPU per read and the other 427 us, for
identical code. The slower task saturated and capped the fleet. The likely
cause is the host type: Fargate ARM64 tasks land on Graviton2 or Graviton3
hosts, and each deploy draws new ones (not verified). Run-to-run differences
between r3 variants are partly this effect.

Every read also logs one INFO span-close line (`FmtSpan::CLOSE` in
`builder/logging.rs`), about 3,800 lines/s at r3 load.

### 4. Database CPU (current ceiling)

With 4 server tasks (r4), the servers had headroom and the database ran at
99% CPU: about 0.28 ms of database CPU per read, so about 7,100 reads/s on 2
vCPU. Remaining waits: CPU, `IPC:ProcarrayGroupUpdate`, `LWLock:LockManager`.

Database CPU per read, from instance CPU (not Performance Insights active
sessions, which leave out protocol and connection work):

| Configuration | DB CPU per read |
|---|---:|
| committed | 0.44 ms |
| async commit | 0.43 ms |
| driver fix | 0.30 ms |
| driver fix + async commit | 0.27 to 0.28 ms |

## Local A/B of the admission call

Postgres 17 in Docker limited to 2 CPUs, normal commits, 10,000 accounts and
sessions, 64 connections, 20 s per variant, a checkpoint before each, three
rounds (results within a few percent). The read-only variant is the same
function with the record insert removed. Docker for Mac fsync is far cheaper
than EBS and there is no TLS, so absolute rates are higher than on RDS; the
CPU per read and the ratios carry over.

| Variant | Commits/read | PG CPU/read | Reads/s on 2 CPUs |
|---|---:|---:|---:|
| committed: raw `sql_query`, record | 2.0 | 212 us | 9,470 |
| driver fix: typed, record | 1.0 | 132 us (-38%) | 15,190 (+60%) |
| driver fix + async commit | 1.0 | 121 us (-43%) | 16,650 (+76%) |
| raw `sql_query`, no record | 2.0 | 149 us (-30%) | 13,580 (+43%) |
| driver fix, no record | 1.0 | 81 us (-62%) | 24,850 (+162%) |

The driver fix removes more cost than dropping the record write does; the
record write costs about 50 us per read on top of the fixed call.

Zero failures in every leg. The counter confirms the rule: at 10,000/s

- Postgres CPU per poll falls by about a third (38% at 2,000/s, 30 to 34%

  that high with Postgres at about 65% is not explained locally; check pool
  acquire wait on the deployed A/B, where the load generator does not share
  the host.

## Changes made during the session (uncommitted)

- `crates/server/src/coordination/postgres/read_records.rs`: admission called
  through a typed `define_sql_function!` returning a record row.
- `crates/server/src/metadata/postgres.rs`: session floor called through a
  typed function; wallet floor CAS moved into
  `guardian_advance_wallet_floor` (migration
  `2026-11-04-000001_advance_wallet_floor`, same SQL, `CREATE OR REPLACE`)
  because Diesel 2.2 cannot express `ON CONFLICT ... DO UPDATE ... WHERE` on
  an insert from a select. The per-signer migration test installs it at its
  intermediate schema point. Postgres suite 94/94.
- `scripts/run-prod-benchmark-ecs.sh`: worker results are rejoined from
  CloudWatch events (a log event holds at most 256 KB) and read through every
  page of the stream (results reached about 790 KB at r4), and accepted only
  once they decode to valid JSON. r2 and r4 were recovered by hand before
  these fixes.
- `scripts/guardian-bench-env.sh`: name guard, tag-ownership checks, exact
  task-family match, bench-only ACK identity, `down --dry-run`, and
  `BENCH_IMAGE_SOURCE=worktree` to build uncommitted changes.

Found, not fixed: `rebuild_url` in `storage/postgres.rs` form-encodes the
`DATABASE_URL` query, so a space becomes `+` and libpq rejects a value such
as `options=-c x=y` (`--x=y` works).

## Not verified

- The Graviton2 / Graviton3 explanation for the per-task CPU difference.
- In r4 Performance Insights reported about 3,300 commits/s for 7,100

  statistics lag at 99% CPU; not explained.

## Next steps

Ordered by expected gain per effort. Items 1 to 3 keep the replay guarantee
(each signed read admitted once, fleet-wide) and full durability; measure each
with the local harness before another AWS run.

1. **Remove the shared fence lock from the read path.** Every admission takes
   `pg_advisory_xact_lock_shared(7310317001)`. Advisory locks cannot use the
   per-backend fast path, so all reads contend on one shared lock-table
   entry, the likely source of `LWLock:LockManager`. Needs a fence design
   that does not lock per read, re-checked with `verify-auth-replay`.
2. **Trim partition routing.** About 25 partitions of `session_read_seen`
   exist at a time (an hour ahead). Fewer partitions ahead, or inserting into
   the current partition directly, cuts locking and planning per insert.
3. **Batch admissions per replica** (one call and one commit for the reads
   that arrive within 1 to 2 ms). Removes the WAL-flush ceiling without async
   commit, and spreads the transaction, round-trip and TLS cost.
4. **Server cost per read** (0.43 to 0.82 ms): profile the signature check and
   the per-read log line. Servers scale out, so this is cost rather than a
   ceiling, but plan replica headroom for the slowest host type.
5. **Replay-policy decision** (separate security review, excluded by the 317
   spec): a per-replica in-memory record with a start-time fence (a copy of a
   captured read usable at most once per replica), or window-only reads.
   Locally the no-write variant costs 81 us of database CPU per read against
   132 us with the record. Only if 1 to 3 fall short.
6. **Then one AWS run** of the best local variant on `db.m7g.large` at r4 and
   r5 (10,000/s), with `BENCH_IMAGE_SOURCE=worktree`, and an r1 to r2 run
   with wallet credentials to cover the wallet floor CAS.
7. Fix the `DATABASE_URL` form-encoding bug.

## Cost context

`db.m7g.large` is general purpose (Graviton3, 2 vCPU, 8 GiB), the right
family for many small transactions on a small data set. On-demand
PostgreSQL in us-east-1 is about $0.168/h (about $123/month single-AZ, about
$245/month Multi-AZ); each size up doubles that. Reaching 10,000 reads/s by
instance size alone would mean an `xlarge` or `2xlarge` (about $490 to $980
per month Multi-AZ), spent mostly on per-read overhead that items 1 to 3
remove.

## Reproducing

- Environment: `scripts/guardian-bench-env.sh up|status|down [--dry-run]`;
  see the "Devnet bench environment" section of `benchmarks/prod-server/README.md`.
- Runs: `./scripts/run-prod-benchmark-ecs.sh --profile
  benchmarks/prod-server/profiles/devnet-bench-r3-5k.toml --workers 4
  --no-cleanup --image-uri <worker image> --skip-build`, with
  `BENCH_ECR_REPO_NAME=guardian-bench`.
- Async commit (experiment only): append
  `&options=--synchronous_commit%3Doff` to the task's `DATABASE_URL` and
  register a new revision.
- Run reports: `benchmarks/prod-server/reports/<run id>/` (not committed).
