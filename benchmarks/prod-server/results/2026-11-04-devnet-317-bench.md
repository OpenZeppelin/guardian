# Feature 317 deployed benchmark: session reads on AWS, 2026-11-04 and 2026-11-05

Session-read capacity of the 317 build on AWS and what limits it, measured on
a temporary `guardian-bench` service next to devnet (created by
`scripts/guardian-bench-env.sh` with the `devnet-bench-*` profiles, both in
#588) and torn down after each session. Nov 4 measured the build that still
recorded every nonce poll; Nov 5 measured the window-only nonce poll.

## Summary

- The window-only nonce poll removes the ceiling Nov 4 found (one durable
  commit per read): on `db.m7g.large` the poll path went from saturating at
  about 4,850 polls/s (p95 about 2.2 s, writes starved) to holding 5,000/s at
  p95 7 ms and 7,500/s with every load-generator worker's p95 under 150 ms
  (78% database CPU). It saturates near 10,000/s.
- On `db.m7g.xlarge` the database runs 10,000 polls/s at 51% CPU, but one
  of 4 server tasks saturated, so 10,000/s is not yet qualified for latency.
- Cost per 1,000 nonce polls/s: about 0.2 vCPU of database (Graviton3) and
  0.5 vCPU of Guardian server. Sizing guidance built on these runs is in
  `docs/SERVER_AWS_DEPLOY.md`, "Sizing for session reads".
- Zero failures in every run. Past a ceiling the closed-loop clients slow down
  rather than fail, so throughput and latency, not failures, show overload.
- Latencies are per-worker summaries, not fleet percentiles (see the caveat
  below).

## Setup

- Bench environment: ECS service `guardian-bench` in `guardian-cluster`
  (devnet account), built from `0f0c600b` (server 0.19.0-rc.1), Fargate ARM64,
  2 tasks of 2 vCPU / 4 GB (4 tasks in the last run), pool size 32 per task.
  Database: RDS PostgreSQL 17.9, `db.m7g.large`, single-AZ, gp3 100 GB, direct
  route (no RDS Proxy), `sslmode=require`, Performance Insights on.
- Server settings: canonicalization off (bench-only image patch, so pushed
  deltas commit at once), proving, release sweep and rate limiting off,
  `GUARDIAN_ENV=prod`. Bench-only ACK identity from `ack-keygen`, signed in
  memory, so write latency excludes the KMS round trip a KMS-backed
  deployment pays.
- Load: `run-prod-benchmark-ecs.sh` with 4 Fargate workers in the same VPC,
  session credentials (ECDSA), 60 s warmup, 420 s measured. Readers poll the
  canonical nonce; 3 readers per writer are cosigners and fetch state after
  each write; writers push every 10 s (proposal, approval, push).

  | Profile | Users | Readers / writers | Target nonce polls/s | Writes/s |
  |---|---:|---|---:|---:|
  | `devnet-bench-r1-1k` | 2,010 | 2,000 / 10 | 1,000 | 1 |
  | `devnet-bench-r2-2500` | 5,025 | 5,000 / 25 | 2,500 | 2.5 |
  | `devnet-bench-r3-5k` | 10,050 | 10,000 / 50 | 5,000 | 5 |

## Nov 4: every nonce poll recorded

Same environment and profiles, 2 server tasks unless noted, normal commits.

| Run | Build / setting | Nonce polls/s | Nonce p50 / p95 / p99 ms (weighted) | Writes/s (target) | DB CPU |
|---|---|---:|---|---|---:|
| r1 `20261104T095910Z-34cb4fe6` | as committed then | 1,000 | 4.3 / 5.7 / 17.7 | 1 (1) | 29% |
| r2 `20261104T102822Z-595dcdf7` | as committed then | 2,500 | 4.9 / 13.9 / 59.5 | 2.5 (2.5) | 63% |
| r3 `20261104T113649Z-2906c78c` | as committed then | 4,129 | 658 / 3,099 / 3,523 | about 3 (5) | 90% |
| r3 `20261104T135224Z-6004ca5e` | typed SQL calls | 4,853 | 528 / 2,218 / 2,316 | 2.9 to 3.5 (5) | 73% |
| r4 `20261104T143557Z-f9e79f71` | typed calls + async commit (experiment), 4 tasks | 7,102 | 508 / 2,446 / 2,644 | 4.97 (7.5) | 99% |

What limited it:

- **One durable commit per read.** Every session read, nonce poll included,
  inserted a record and committed; at r3 most of 20 active database sessions
  waited on `LWLock:WALWrite`. Async commit removed the wait but gained only
  9%, because database CPU was next.
- **Raw SQL prepared on every call.** Diesel does not cache `sql_query`, so
  each call was a prepare round trip (its own transaction) plus the execution:
  about 2 commits per read. Calling the admission and floor functions through
  `define_sql_function!` brought it to 1 commit per read, database CPU per read
  from 0.44 to 0.30 ms and +18% throughput. This is in the PR.
- **Uneven server tasks.** With the database idle, one of two tasks spent
  817 us of CPU per read and the other 427 us for the same code (likely
  Graviton2 against Graviton3 hosts; not verified), and the slower one capped
  the fleet.
- **Per-read log line.** The INFO span-close line costs about 15% of server
  CPU and 2 to 3 times the p99 at 4,000 polls/s (local A/B); the nonce poll's
  span is now `debug`.

Locally, a read-only admission (no record) cost 81 us of Postgres CPU per read
against 132 us with the record, which is what led to the window-only nonce
poll (`speckit/features/317-secure-scalability/decision-nonce-read-window.md`).
A local A/B of the change itself (Docker, 2-CPU Postgres) showed about a third
less Postgres CPU per poll and 34% more polls where Postgres was the limit,
before the laptop ran out of CPU.

## Window-only nonce poll on AWS (2026-11-05)

Same bench environment and instance class (`db.m7g.large`, fresh database),
built from `202d6851` (window-only nonce poll), 4 workers, session
credentials, 60 s warmup, 420 s measured. Only leg B was run; the "before"
is the Nov 4 r3 run with the driver fix (`20261104T135224Z-6004ca5e`). CPU
is the per-minute CloudWatch average over the measured window.

**Latency caveat.** The harness's distributed aggregator averages each
worker's p50, p95 and p99, weighted by request count
(`benchmarks/prod-server/src/distributed.rs`). That is not a fleet
percentile, and worker artifacts carry only summary percentiles, so true
fleet percentiles cannot be rebuilt for these runs. The table gives the
weighted figures for continuity with earlier reports, plus the range of
the per-worker p95 where the artifacts survive (all four runs were
checked during review; the r3 and r4 artifacts went with the bench log
group at teardown). No latency target is established until the
aggregator merges histograms.

| Run | Tasks | Nonce polls/s | Nonce p50 / p95 / p99 ms (weighted) | Nonce p95 per worker | Writes/s (target) | Write p50 / p99 (weighted) | DB CPU | Server CPU per task |
|---|---:|---:|---|---|---|---|---:|---:|
| Nov 4 r3 `20261104T135224Z-6004ca5e` (recorded) | 2 | 4,853 | 528 / 2,218 / 2,316 | n/a | 2.9 to 3.5 (5) | 3.8 s / 21.3 s | 73% | 85% / 57% |
| r3 `20261105T120128Z-4b510922` | 2 | 5,000 | 2.0 / 7.3 / 57 | 6 to 8 ms | 5.0 (5) | 71 ms / 366 ms | 53% | 65% |
| r4 `20261105T122056Z-1257e7cc` | 4 | 7,500 | 4.3 / 91 / 229 | 49 to 140 ms | 7.5 (7.5) | 119 ms / 746 ms | 78% | 46% |
| r5 `20261105T123115Z-6e824a31` | 4 | 9,944 | 1,602 / 2,054 / 2,190 | 2,029 to 2,091 ms | 6.6 (10) | 14.8 s / 20.3 s | 99.5% | 63% |
| r5 on `db.m7g.xlarge` `20261105T125558Z-02ba9264` | 4 | 9,995 | 84 / 790 / 1,259 | 75 to 1,356 ms | 9.9 (10) | 711 ms / 9.7 s | 51% | 61% (busiest 96 to 98%) |

Zero failures and zero wallet-signed fallbacks in every run, and request
totals reconcile across worker artifacts. Both r5 harnesses lost their AWS
session while waiting for the workers; their reports were rebuilt from the
worker log streams with the same `aggregate` step. The last row ran after
resizing the same instance to `db.m7g.xlarge` (4 vCPU), with the same 4
server tasks. Runs are 7 minutes each: enough for preliminary sizing, not
for a production capacity claim.

- The window-only poll removes the Nov 4 ceiling: r3 holds its target with
  every worker's p95 under 10 ms (Nov 4: saturated at 4,853/s, p95 about
  2.2 s), and writes are no longer starved by reads.
- r4 (7,500/s) keeps every worker's nonce p95 under 150 ms with database
  CPU at 78%.
- r5 saturates `db.m7g.large`: 99.5% CPU, about 3.8 active sessions on 2
  vCPU. Throughput still reaches 9,944/s because clients are closed-loop,
  but the excess is queueing (every worker's p95 about 2 s) and writes fall
  to 6.6/s.
- Database CPU is close to linear, about one point per 100 polls/s
  (53%, 78%, 99.5%). The highest rate that keeps p95 under 1 s on
  `db.m7g.large` lies between the measured 7,500/s and 9,944/s; 8,500 to
  9,000/s is an interpolation, not a measurement.
- Performance Insights: `guardian_serve_session_read` is the top statement
  (about 0.17 ms per call, one call per poll); the recorded path
  (`guardian_admit_session_read`) is down to the state-fetch rate (about
  15 to 22 calls/s).
- On `db.m7g.xlarge` the database runs 10,000 polls/s at about 51% CPU
  (about 1.2 average active sessions on 4 vCPU, mostly `Client:ClientRead`),
  so it is no longer the limit. The servers are: one of the 4 tasks ran at
  96 to 98% CPU while the average was 61%, the per-worker nonce p95 ranged
  from 75 ms to 1,356 ms, and the write tail reached 9.7 s (p99, weighted)
  and 17.3 s (max). The cause of the uneven spread is not established. The
  bench reaches the servers through Cloud Map DNS, which may pin a worker's
  connections to one task; that fits the per-worker spread but was not
  verified, and an ALB balancing gRPC per request does not by itself
  guarantee equal CPU per task. A 2 vCPU task saturates at about 3,000 to
  3,500 polls/s. Worker tasks used about 38% of their CPU.
- Cost per 1,000 nonce polls/s, consistent across r3, r4 and r5: about 0.2
  vCPU of database (Graviton3) and about 0.5 vCPU of Guardian server
  (average across tasks).

Not yet qualified: 10,000 polls/s within the latency target. Open:

1. Merge latency histograms in the aggregator, so fleet p95 and p99 are
   measurable.
2. Repeat r5 with even load (through the production ALB, with requests/s
   and CPU per request reported per server task), then the sustained
   10,000/s profile.
3. Run sustained load with canonicalization on (100 writers), which these
   runs do not cover.

## Serving call variants (local pgbench, 2026-11-05)

Postgres 17 capped at 2 CPUs, 20,000 seeded accounts with live sessions and
state heads, 32 clients over prepared statements, 30 s per round, the
variants alternated over two rounds. All three return identical rows for
served (with and without head), no state, no account, unknown, revoked and
expired sessions, and both window edges.

| Variant of `guardian_serve_session_read` | tps (round 1, round 2) |
|---|---|
| current PL/pgSQL, four statements | 32,303, 32,847 |
| PL/pgSQL, one joined query | 29,481, 30,437 |
| SQL-language function, one query | 7,295, 7,231 |

The current function is the fastest: its small statements keep cached plans,
and a SQL-language function is planned on every call in Postgres 17. The
function body costs about 0.06 ms of CPU per call locally against about
0.2 ms per poll on RDS, so most of the RDS cost is per statement (TLS,
protocol, transaction, monitoring) on slower cores, and the server already
makes one database call per poll. Not changed.

## Cost context

`db.m7g.large` is general purpose (Graviton3, 2 vCPU, 8 GiB), the right
family for many small transactions on a small data set. On-demand
PostgreSQL in us-east-1 is about $0.168/h (about $123/month single-AZ, about
$245/month Multi-AZ); each size up doubles that. With the window-only nonce
poll, `db.m7g.large` held 7,500 polls/s and `db.m7g.xlarge` (about $245/month
single-AZ, $490/month Multi-AZ) ran 10,000 polls/s at 51% CPU. The extra
cost now buys capacity for the poll itself (about 0.2 vCPU per 1,000
polls/s), not per-read commit overhead.

## Reproducing

- Environment: `scripts/guardian-bench-env.sh up|status|down [--dry-run]`
  and the `devnet-bench-*` profiles, added by #588; see its "Devnet bench
  environment" section of `benchmarks/prod-server/README.md`.
- Runs: `./scripts/run-prod-benchmark-ecs.sh --profile
  benchmarks/prod-server/profiles/devnet-bench-r3-5k.toml --workers 4
  --no-cleanup --image-uri <worker image> --skip-build`, with
  `BENCH_ECR_REPO_NAME=guardian-bench`.
- Async commit (experiment only): append
  `&options=--synchronous_commit%3Doff` to the task's `DATABASE_URL` and
  register a new revision.
- Run reports: `benchmarks/prod-server/reports/<run id>/` (not committed).
