# Feature 317 read ramp, 1 vs 2 servers (local, Docker-capped), 2026-11-02

Session reads under `unique`, ramped from 1,000 to 7,500 polls/s against one
and two server instances, to see where capacity runs out and whether a second
instance helps. Local, resource-capped: shows bottlenecks and scaling, not
absolute deployed capacity.

## Setup

- Apple M-series laptop (10 cores, 4 performance), Docker Desktop VM with all
  10 cores. Everything runs in Docker on one network, so no port forwarding
  sits in the path.
- Servers: the 317 working tree (release build, `postgres` feature) with
  canonicalization switched off through a local-only patch. Each instance is
  capped at 2 CPUs and 2 GB (`docker run --cpus 2`), pool size 32, rate limits
  lifted, one shared ACK key.
- Postgres 17, capped at 2 CPUs and 2 GB, `shared_buffers` 512 MB, default
  durability settings. Fresh database per step.
- Load: `benchmarks/prod-server` `worker-run`, two shards in their own
  containers (no CPU cap). With two servers each shard talks to its own
  server; with one server both shards use it, so the load generator is the
  same in both legs.
- Profile: ECDSA session credentials. Readers poll the canonical nonce every
  2 s and fetch state when it changed; writers (readers / 200, the target's
  ratio) write every 10 s, a write being proposal, approval and push; three
  readers per writer are its cosigners. 60 s warmup, 240 s measured.

## Findings

- **Postgres is the first limit, at about 5,000 polls/s for 2 CPUs.** With
  two servers at 5,000/s the servers had headroom (124% of 200% each) while
  Postgres ran at 185% of its 200% cap; requests then queued for pool
  connections and p95 rose to 729 ms. At the 7,500/s step neither setup
  reached the rate (4,200 to 4,400/s) and Postgres was at its cap.
  Postgres used about 0.3 to 0.4 ms of CPU per poll (74% at 2,500/s in
  this run, 99% in the back-to-back run below), so 10,000 polls/s needed
  3 to 4 Postgres cores before headroom with this build; after the fixes
  below it is about 0.3 ms.
- **One 2-CPU server saturates at about 5,000 polls/s.** It used 91% at
  2,500/s and its full cap at 5,000/s, about 0.37 ms of CPU per poll, which
  matches the 0.4 ms from the uncapped run. 10,000/s therefore needs about
  4 server CPUs at 100%, so 3 to 4 tasks of 2 vCPU with headroom (more on
  Graviton, whose cores are slower than these).
- **A second server helps until Postgres saturates.** At 2,500/s it cut p95
  from 103 ms to 37 ms and pool wait from 14 ms to 3.4 ms; at 5,000/s it
  halved latency but could not fix it, because the database was the limit.
- **Writes suffer first under saturation.** Writes take several pool
  checkouts and queue behind reads: write p95 went from 60 ms to 5.5 s (two
  servers) when reads moved from 2,500 to 5,000/s.
- **No correctness issues under load:** no replay rejections, no failed
  admissions, no failed writes at any step, including the saturated ones.
- At 1,000/s the server time per poll (6 ms) is higher than in the uncapped
  native run (1.5 ms): container networking and the 2-CPU cap on Postgres add
  latency. Compare steps within this file, not with the native run.

## What it means for the 10,000/s target

- The read path scales horizontally on the server side as expected; the
  capacity question moves to the database. On RDS, size for at least about
  3 database vCPUs of headroom-free work at 10,000 polls/s from this
  measurement, that is a 4-vCPU instance at high utilisation or an 8-vCPU
  one with margin, before measuring on RDS itself.
- Which statements cost the Postgres CPU is broken down in the sections
  below, with the two fixes it led to and what is left after them.

## Where Postgres spends its time

Same setup, two servers at 2,500 polls/s, with `pg_stat_statements`
(`track = all`, so statements inside the SQL functions are listed too) over
168 s of the measured window. Tracking itself raised Postgres CPU from about
75% to 104%, so the shares below matter, not the absolute numbers.

| Statement | Calls | Share of execution time | Mean |
|---|---:|---:|---:|
| `guardian_admit_session_read` (whole call) | 419,945 | 90% | 0.134 ms |
| of which `guardian_record_session_read` | 419,945 | 50% | 0.073 ms |
| of which the read-record `INSERT` | 419,945 | 23% | 0.033 ms |
| of which the metadata `auth_version` lookup | 419,945 | 7% | 0.011 ms |
| of which the session lookup | 419,945 | 5% | 0.007 ms |
| of which the shared advisory lock and fence read | 421,000 each | 3% each | 0.004 to 0.005 ms |
| state head read (`commitment`, `nonce`) | 418,695 | 7% | 0.010 ms |
| `SELECT 1` | 850,177 | 1% | 0.001 ms |
| everything else (writes, sweeps) | | under 2% | |

- Statement execution added up to 62 s, about 0.37 cores, while the container
  used about 0.75 to 1 core: per statement, the rest is protocol, parse and
  commit work that `pg_stat_statements` does not count. That makes the number
  of statements matter as much as their cost.
- `SELECT 1` was half of all statements: two per poll. It is the connection
  pool's health check, which diesel-async's default recycling method
  (`Verified`) runs on every checkout, once for the metadata pool and once for
  the storage pool. Each costs a database round trip before the real query.
- The read record writes about 300 bytes of WAL per poll (122 MB for 420,000
  reads).

## Pool health check A/B

Two servers, back to back, the same build except the pool's recycling method:
`Verified` (current) against `Fast` (no test query; connections the server
closed are still discarded, because diesel checks `is_closed` on checkout).

| Polls/s | Recycling | Nonce p50 / p95 / p99 ms | State p95 ms | Write p95 ms | Pool wait | Servers CPU | Postgres CPU |
|---:|---|---|---:|---:|---:|---:|---:|
| 2,500 | `Verified` | 15.1 / 159 / 713 | 73 | 237 | 25 ms | 127% | 99% |
| 2,500 | `Fast` | 10.2 / 51 / 150 | 24 | 96 | 7.4 ms | 109% | 79% |
| 5,000 | `Verified` | 136 / 1,916 / 2,280 | 1,315 | 14,579 | 410 ms | 252% | 192% |
| 5,000 | `Fast` | 32 / 409 / 885 | 236 | 1,531 | 79 ms | 229% | 159% |

- Without the health check, Postgres used about 20% less CPU at 2,500/s and
  stopped being saturated at 5,000/s; p95 dropped about 3 to 5 times and
  write p95 about 2.5 to 10 times. Zero failures in all four legs.
- The `Verified` leg at 2,500/s was slower than the same step in the ramp
  above (p95 159 ms against 37 ms, Postgres 99% against 75%): run-to-run
  variation on this laptop is large, so compare legs run back to back.
- Through RDS Proxy every round trip costs about 13 ms (measured Oct 29), so
  the two health checks add about 26 ms to every request there, on top of
  the database CPU.
- Risk of `Fast`: a connection that died without being closed (a half-open
  TCP connection, for example during a failover) is only found when a query
  fails on it, so one request fails instead of the pool quietly reconnecting.

## After the two fixes

Both fixes in the working tree: the pool reuses connections without a test
query (`RecyclingMethod::Fast`), and a session nonce poll gets the canonical
state head from the admission call (`guardian_admit_session_read` with
`p_with_head`), so it is one database call and one pool checkout. Two
servers, the build before (`base`) and after (`opt`) the fixes run back to
back at each step.

Zero failed operations in every step.

- Storage-pool checkouts per poll fell from 1.03 to 0.03 (the rest are
  writes and state fetches): a nonce poll is one database call.
- Postgres CPU per poll fell about a quarter: 74% against 99% at 2,500/s,
  about 0.30 ms against 0.40 ms. p50 and p95 halved at 1,000 and 2,500/s.
- At 5,000/s the old build saturated Postgres and fell behind (4,100/s); the
  new one held the rate with Postgres at 154%, but p95 was still 1.3 s. The
  servers waited 330 ms on average for a metadata-pool connection while
  neither Postgres nor the servers were at their cap: with 32 connections per
  server and admissions slower on a busy 2-CPU database, the pools ran out
  first. A larger pool does not help (below).
- At 7,500 and 10,000/s both builds were past capacity, Postgres was at its
  cap, and the laptop itself was near its limit (the containers used 7.5 to
  8 of its 10 cores), so these two steps show overload, not a capacity
  figure.
- Capacity on a 2-CPU Postgres moved from about 4,000 to about 5,000 polls/s
  with acceptable latency. At about 0.3 ms of Postgres CPU per poll, 10,000
  polls/s still needs about 3 database cores before headroom.

## Pool size at 5,000 polls/s

The fixed build, two servers, 5,000 polls/s, pool size 32 against 64 per
server (both the storage and the metadata pool), back to back.

| Pool per server | Polls/s | Nonce p50 / p95 / p99 ms | Write p95 ms | Metadata pool wait | Servers CPU | Postgres CPU |
|---:|---:|---|---:|---:|---:|---:|
| 32 | 4,999 | 23 / 587 / 1,210 | 1,768 | 105 ms | 232% | 155% |
| 64 | 4,931 | 107 / 949 / 2,451 | 6,819 | 257 ms | 254% | 170% |

- A bigger pool made it worse: more connections running at once on 2
  Postgres CPUs raised Postgres CPU and every percentile. The pool wait was
  where the backpressure showed, not its cause; the limit is Postgres
  throughput on 2 CPUs, which this load reaches at around 5,000 polls/s.
  Keep the pool at 32 per server and size the database instead.
- The 32-connection leg here had p95 587 ms against 1,344 ms for the same
  build and step in the run above. Near the knee, run-to-run variation on
  this laptop is large; compare only legs run back to back.

## Slimming the admission function

A candidate rewrite of `guardian_admit_session_read` as one plpgsql body: one
joined account and session lookup, the read-record logic inlined instead of
called, `OUT` parameters instead of `RETURN QUERY`, the checks in the same
order. Measured with `pgbench` (16 clients, extended protocol) against one
seeded account and session, on an uncapped Postgres container, alongside
probes that split the cost:

| Probe | Commit flushed | Calls/s |
|---|---|---:|
| current admission | yes | 26,763 and 24,748 (before a restart); 5,446 to 15,863 (after) |
| slim admission | yes | 25,887 and 23,574 (before); 12,306 (after) |
| current admission | no | 28,158 / 86,924 / 58,044 |
| slim admission | no | 28,195 / 88,340 / 43,904 |
| read-record insert alone | no | 85,454 / 88,650 / 45,284 |
| account, session and state lookups alone (no write) | n/a | 92,847 / 80,096 / 119,404 / 123,871 / 113,362 |

- The slim version is no faster: within noise of the current one in every
  pairing. It was not applied.
- With the commit flush off, the whole admission costs the same as the bare
  insert into `session_read_seen`: the lookups, the shared lock, the fence
  read and the function overhead are not measurable next to the write.
- The write itself, a partitioned-table insert plus its WAL record, costs
  roughly 1.4 times a read-only lookup at best. The commit's WAL flush comes
  on top and dominates whenever flushes are slow; on this laptop's Docker VM
  their cost changed by a factor of five between runs, so its share cannot be
  measured here.
- Run-to-run variation on this machine is large even with flushing off
  (28,000 to 87,000 calls/s for the same probe), so only ratios within one
  round are meaningful.

What this leaves: a session read now costs one durable write and nothing
else worth optimising in SQL. Lowering that further means either not
flushing the read record at commit (`synchronous_commit = off` for the
admission, which lets reads accepted in the last moments before a database
crash be replayed and needs security review), fewer reads (a push stream
instead of polling), or more database capacity.

## Caveats

- One laptop: load generator, servers and Postgres share 10 cores. In the
  saturated steps of the first ramp the containers used 5 to 6.5 cores in
  total, so the laptop was not the limit there; after the two fixes the 7,500
  and 10,000/s steps used 7.5 to 8 cores and show overload only. Its cores
  also differ from Graviton's.
- Local Docker volume, not RDS storage; no RDS Proxy.
- 2,000 to 20,000 readers seeded per step, not the 100,000 accounts of the target.
- Canonicalization off.
- One run per step.
- Artifacts (profiles, worker artifacts, server metrics, CPU samples) are in
  the session scratchpad, not in the repository.
